Billing Module

# Overview

The Billing Module manages subscription billing for the Streamsphere platform using Stripe as the payment provider. It handles:
* Customer Creation
* Subscription Checkout
* Billing portal access
* Invoice tracking
* Subscription status
* Webhook processing
* Email notifications
* Admin billing analytics

The architecture is designed to be scalable, event-driven, and fault tolerant using:

* Stripe API for payments
* MongoDB for billing data persistence
* BullMQ for asynchronous processing
* Workers for background tasks
* Webhook queue for reliable event processing

# API Endpoints

* POST /billing/create-customer (Creates a stripe customer for the authentocated user)

Response 
{
    message: Customer Created,
    customer: {}
}

* POST /billing/create-checkout-session (Creates a Stripe checkout session for subscription purchase.)

Request 
{
  "priceId": "price_xxx",
  "stripeCustomerId": "cus_xxx",
  "successUrl": "...",
  "cancelUrl": "..."
}

Response
{
  "url": "checkout_url",
  "id": "session_id"
}

* POST /billing/seed-plan (Imports Stripe pricing data into the local database.)

* GET /billing/status (Returns subscription status for the authenticated user.)

Response
{
  "hasSubscription": true,
  "status": "active",
  "currentPeriodStart": "...",
  "currentPeriodEnd": "..."
}

* GET /billing/portal (Creates a Stripe billing portal session where users can:
update payment method
view invoices
cancel subscription)

* GET /billing/resend-payment-portal (Sends an email with a billing portal link.)

* GET-Admin /billing/admin/subscriptions (These endpoints allow administrators to inspect billing activity.)

Supports filtering:
- status
- email
- pagination

* GET-Admin /billing/admin/invoices (List Invoices)
* GET-Admin /billing/admin/webhooks (List Webhooks)

* POST-Admin /billing/admin/replay-webhook (Allows admins to replay failed Stripe events.)

* POST /billing/webhook (Stripe sends events to the application webhook endpoint.)
Weebhook Handler:
- Verifies Stripe signature
- Constructs Stripe event
- Passes event to the webhook service
- Stores raw event in DB
- Enqueues event to webhook queue

# Webhook Event Processing (The system processes events asynchronously using BullMQ workers.)

* Supported events include:
- checkout.session.completed
- invoice.payment_succeeded
- invoice.payment_failed
- customer.subscription.updated
- customer.subscription.deleted

* Worker responsibilities:
- create subscriptions
- update subscription status
- store invoices
- trigger email notifications

# Email Notification System (Emails are sent asynchronously using the Email Worker.)

* Supported notifications:

Event	             |   Email
payment_success	     |  Payment confirmation
payment_failed	     |  Payment failure alert
payment_update_link	 |  Update payment method

Example template usage:
- payment success email
- payment update link

# Billing Reconciliation Script (A reconciliation script ensures Stripe and MongoDB remain consistent.)

Steps performed:
- Fetch subscriptions from Stripe
- Compare with local database
- Detect mismatches
- Auto-fix status inconsistencies

# Fault Tolerance & Reliability (The billing system includes several reliability mechanisms.)

* Idempotent Webhooks (Webhook events are stored before processing to avoid duplication.)
* Background Workers (Heavy tasks are processed asynchronously using BullMQ.)
* Retry Strategy (Failed jobs can be inspected and retried.)

# Key Design Decision

* Queue-based Webhook Processing (Instead of processing Stripe events synchronously:)
Stripe → Webhook → Queue → Worker
Benefits:
- prevents webhook timeouts
- improves reliability
- implement retry job failed Mechanism
- allows retries
- Get the all Failed Jobs which also failed after retry mechanism and also monitor that by (node src/modules/billing/workers/failedJobHandler.ts)

* Event Storage
Raw webhook events are stored for:
- auditing
- replaying failed events
- debugging

* Admin Observability
Admin APIs allow monitoring of:
- subscriptions
- invoices
- webhook events

* Security Considerations
Security measures implemented:
